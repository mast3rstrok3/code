# Workflow catalog

The server owns a compiled workflow catalog with three linked record types: workflows contain ordered steps, skill-backed steps reference canonical catalog skill IDs, and skills reference deduplicated supporting document IDs. Internal workflow prompt IDs remain separate from catalog skill IDs, workflow presets identify definitions, and durable workflow IDs identify individual runs.

`server.getWorkflowCatalog` exposes the read-only catalog to clients. `server.getWorkflowPrompts` remains available for older clients and is derived from the same registry.

The source of truth is `apps/server/src/provider/WorkflowPromptRegistry.ts`. T3 workflow prompts remain inline constants. Direct Build skills and their supporting references are generated into `mattPocockEngineeringSkills.generated.json` by `apps/server/scripts/sync-matt-pocock-engineering-skills.mjs`; the generated snapshot records the exact upstream commit and is compiled into the server. `buildWorkflowCatalog()` runs once at module load and validates the whole graph: a step referencing an unknown skill ID throws, and two documents sharing an ID with different content throw a conflict error, so a broken catalog fails the server at startup rather than at runtime.

## Skill prompt anatomy

The catalog includes every skill in [Matt Pocock's engineering collection](https://github.com/mattpocock/skills/tree/main/skills/engineering) as an individual direct Build skill. These entries keep the upstream `SKILL.md` body and bundle supporting files into the selected turn so invocation does not depend on provider-local skill installation. Internal workflow prompts remain T3 adaptations: the upstream body appears near-verbatim first, doc references use `workflow_doc_get`, and T3-specific behavior lives in trailing adapter and directive sections.

Catalog construction maps those internal prompts back to canonical engineering skill IDs. For example, `implementation.tdd.codex` executes the adapted workflow worker while the visible workflow step points to `matt-pocock.tdd`. T3-native stages such as Merge Gate and Browser App Review keep their own catalog entries. The final skill list is title-sorted and carries explicit `buildModes`, `workflowIds`, and `docIds` relationships.

The registry contains one independent Grilling primitive and two compositions. Product Grill adds codebase grounding, product-decision scope, the structured-question adapter, and the minimal `product-intent-locked` handoff; its two selectable preset prompt IDs fix the intent kind up front. The old `product.fix.codex` prompt remains registered only so historical runs can be decoded and resumed. Engineering Grill adds the complete domain-modeling discipline and the Planning handoff, with the same structured-question adapter on its interactive prompt. The upstream `shared.grilling.codex` primitive remains verbatim. Full Feature uses a separate automatic adapter that keeps the design tree, dependency frontier, fact-finding, domain-modeling, and completeness requirements, but resolves every engineering decision internally from the locked Product Grill intent instead of asking another round of user questions.

The structured adapter requires T3's `workflow_request_user_input` dynamic tool for every interview round and the final shared-understanding gate. It sends the complete currently unblocked dependency frontier when that frontier contains one through ten questions. Ten is a maximum rather than a target: smaller rounds keep their natural size, and frontiers larger than ten continue in stable design-tree order after the first ten answers. Questions with unresolved dependencies are never combined in one round. Each question has two or three naturally ordered choices with neutral impact or tradeoff descriptions, plus a separate recommendation object whose `optionLabel` references one unchanged option label and whose `rationale` explains the preference. Questions and recommendations are not duplicated in Markdown, and T3's existing free-form answer input remains implicit.

For fresh Codex Product Grill and interactive Engineering Grill sessions, `CodexSessionRuntime` registers `workflow_request_user_input` in `V2ThreadStartParams.dynamicTools`, handles `item/tool/call`, emits the canonical `user-input.requested` lifecycle, and waits on the existing user-input response path before returning the full answer map to Codex. Providers that have no such channel reach the same tool over T3's MCP server: the `user-input` capability, granted only to interactive grill prompt IDs, exposes `workflow_request_user_input`, whose handler appends the ordinary `user-input.requested` activity and parks the tool call in `WorkflowUserInputBroker` until `ProviderService.respondToUserInput` settles it from the client's answer. Claude additionally pins that MCP server to `alwaysLoad` with a long per-call timeout so a grill question is never deferred behind tool search. A parked call still cannot outlast the provider's own ceiling — Claude Code aborts a silent HTTP MCP call at roughly five minutes, whatever timeout the server config carries — so the handler hands back a `waiting` result and a `resumeRequestId` after four minutes and the agent parks on the same id again. The card, its request id, and the answers the user has half-filled all survive those rounds; a round nobody parks on again is retired after a grace window so an abandoned question cannot strand a card on screen. Threads created before either registration fall back to the agent's own question tool in chunks of up to three. T3's stored interaction modes, visible workflow semantics, directives, and Engineering Grill's narrow domain-document write authorization remain unchanged. Automatic Engineering Grill, Wayfinder's separate stages, Spec, tickets, review, implementation, and all other workflow turns use native Default transport. An explicit `plan` interaction mode always retains normal CLI Plan behavior, even if a stale grill prompt ID is attached.

This presentation follows Matt Pocock's separation of options, recommendation, and rationale, but deliberately keeps T3's dependency-frontier batching instead of adopting an exactly-one-question-at-a-time interview rule.

Supporting documents (`context-format`, `adr-format`, `domain-docs`, `agent-brief`, `prototype-logic`, `prototype-ui`, `tdd-mocking`, `tdd-tests`, `tdd-logging`, `preview-browser-qa`) are deduplicated by global ID and back-linked to the skills that carry them. The `tdd-logging` document adapts Boris Tane's MIT-licensed `logging-best-practices` skill to T3 Code's Effect spans and logging pipeline.

Planning tickets extend the upstream To Tickets shape with two T3-native fields. `appReviewEligible` is the programmatic routing tag for tickets that can be verified through a human-style UI review. Eligible tickets also require `appReviewPlanMarkdown`, the durable attachment that names the App Dev Stack surface, UI entry point, actions, visible assertions, and evidence. Both fields live in T3's ticket artifact and never require an external tracker label.

At runtime, guided workflow prompt rendering includes only document metadata in an `available-workflow-docs` block. Registered workflow sessions receive the existing `workflow-artifacts` MCP capability and can call the read-only `workflow_doc_get` tool to retrieve a built-in document by ID. Direct Build skills instead inline their upstream supporting files in a delimited `supporting-skill-docs` block for that one turn. Document content is static server data and contains no project or user state.

## Artifacts and directives

Specs, planning tickets, Wayfinder Maps, and app reviews are durable artifacts in the server's event-sourced projection — not repository files or external tracker issues. This is a deliberate deviation from the upstream skills, which publish to an issue tracker or `.scratch/` files.

The server-hosted live tab used by a Browser App Review is an ephemeral workflow resource. Terminal App Review and workflow-child events close it deterministically; the persisted screenshots, recording, findings, checks, and verdict are the post-review inspection artifacts.

Workflow stages hand results to the orchestration by ending a message with exactly one fenced JSON directive, parsed in `apps/server/src/orchestration/workflowDirectives.ts`:

- `product-intent-locked` — Product Grill finished with the intent kind fixed by its workflow preset.
- `planning-grill-complete` — Engineering Grill finished.
- `planning-spec-artifact` / `wayfinder-map-artifact` — write the durable Spec or Wayfinder Map.
- `planning-tickets-artifact` — store the drafted ticket set against a Spec or map.
- `planning-reviewer-verdict` — the ticket reviewer's per-cycle verdict, including a `ticketEdits` array (entries discriminated by `type`: update / create / delete / update-dependencies) through which the reviewer edits tickets directly. A verdict the parser rejects applies nothing, so ingestion hands the complaint and the exact shape back to the same reviewer thread (`MAX_PLANNING_REVIEWER_VERDICT_RETRIES`) before failing the cycle.
- `implementation-worker-result`, `implementation-merge-gate-result`, `implementation-fix-result`, `implementation-code-review-result` — implementation stage results.
- `workflow-subagent-create`, `workflow-subagent-result`, `workflow-agent-message` manage one-child handoffs and messaging. `workflow-subagents-create` remains parseable for historical records, but runtime rejects a new request with more than one child before creating a thread.

Concurrency is scoped by step. Every unblocked ticket may run concurrently because each ticket has its own cadence, worktree, branch, and singleton ticket scope. Within a ticket, only one ticket-scoped step thread is active. Root-scoped Planning, integration, combined App Review, and Code Review steps also run one active thread at a time. One parent may have one unfinished child handoff, and provider-native agents or T3 workflow children cannot create multiple threads for the same step scope. A rejected multi-child handoff records a `workflow.directive.rejected` activity and resumes the parent with instructions to finish the step itself. Existing persisted batches remain readable and may settle normally.

Workflow threads read canonical artifacts through the read-only `workflow-artifacts` MCP toolkit: `workflow_context_get`, `workflow_spec_get`, `workflow_wayfinder_map_get`, `workflow_tickets_list`, `workflow_ticket_get`, `workflow_app_reviews_list`, `workflow_app_review_get`, and `workflow_doc_get`. Interactive grill threads additionally hold the `user-input` capability and its single write-side tool, `workflow_request_user_input`.

## Composer workflow presets

The composer groups five presets under Plan and Engineering. Quick Plan, Fast Plan, Fast Engineering, and Engineering Workflow are launchable. Wayfinder is visible but disabled while its planning phase is under development. Previously shipped Fast Feature, Full Feature, standalone Planning, standalone Implementation, Fix, and App Review identities remain decodable for historical runs.

Quick Plan and Fast Plan use the existing Plan workflow controller. Their root turn uses the provider's native `plan` interaction mode and `planning.fast-feature.codex`; a proposed plan launches the existing Build controller in the prepared worktree. `ProductWorkflowReactor` consumes canonical `user-input.requested` activities for only these two presets. It chooses a valid `recommendation.optionLabel`, otherwise the first option label, otherwise `Use your best judgment and continue.` The resulting `thread.user-input.respond` command uses the request ID in its deterministic command ID, and startup reconciliation repeats unresolved requests safely after a restart.

Fast Engineering and Engineering Workflow share the Planning and Implementation controllers. Both begin with Grill with Docs, produce a Spec and reviewed tickets, then launch Implementation in the same prepared workspace. Wayfinder will replace Grill with Docs with its separate Wayfinder phase.

Each definition supplies `ImplementationWorkflowSettings` defaults. The composer copies them into `workflowImplementationSettings` on the thread, and that durable run configuration becomes the Implementation skip list. Quick Plan disables combined App Review, final Code Review, pull-request creation, and babysitting. Fast Plan enables all four. Fast Engineering disables ticket and combined App Reviews but keeps Code Reviews and pull-request automation. Engineering Workflow enables the full sequence. Ticket App Reviews use ticket skip targets; the combined App Review uses its run skip target. Pull-request creation and babysitting are normalized as a dependency.

App Review remains independently launchable from its panel and reusable as a nested stage. It is not a composer preset.

The following preset descriptions document historical runs and the controllers reused by Engineering Workflow.

### Fast Feature

The workflow has four visible stages: Planning → Building → App Review → Code Review. It first creates its dedicated branch and worktree from the selected branch, then starts directly in CLI Plan mode with `planning.fast-feature.codex`. That prompt requires the proposed plan to carry an ordered Build topology with workstreams, dependencies, ownership, validation, and final integration work. It also carries an ordered App Review topology with browser acceptance lanes, setup, state reset needs, and expected observations. Temporary branches use `worktree/<token>` and their directories use `worktree-<token>`; first-turn semantic renaming removes the temporary prefix entirely. In a detached bootstrap path, the repository-declared setup terminal must exit successfully before AppDevStack creation is requested; repositories without a setup script are ready immediately. After setup, bootstrap reuses the AppDevStack already registered for that exact worktree and branch or creates it when none exists. At every provider turn boundary, the server injects the projected worktree path and branch plus a bounded live lookup of that worktree's AppDevStack. A missing stack is described as pending dependency readiness, while a registered stack contributes its exact id and state and, once healthy, its frontend URL. The context forbids runtime evidence from unmatched host containers, databases, or stacks. Once the temporary branch has its semantic name, its proposed plan launches one Build child. That thread executes every workstream in order, integrates the result, runs focused checks, and commits into the shared worktree. The inherited AppDevStack is then probed. The durable App Review thread exercises every planned acceptance lane in order against that stack and owns recording, screenshots, findings, the verdict, and repairs. Code Review runs its Standards and Spec passes in order, applies fixes, commits, and publishes the pull request into the starting branch. Pull-request creation is the human handoff. Failed or exhausted App Review runs continue best-effort and are called out explicitly on that pull request.

### Full Feature

Before Product Grill, Full Feature creates one dedicated branch and worktree from the branch the user selected, then starts the thread immediately. Worktree setup runs concurrently with the Grill and gates early AppDevStack creation. Product Grill is the only user-interactive gate. After the user confirms the product intent, the same thread enters the complete Planning workflow at the automatic Engineering Grill, where the model resolves the engineering and domain design tree from the locked intent and codebase without asking the user. Spec authoring, tickets, ticket review, and the complete Implementation workflow then continue automatically in that same workspace. Implementation runs in its own controller sub-thread but reuses the Planning worktree, branch, and stack; only ticket TDD workers branch into child worktrees.

### Wayfinder

For efforts too large or uncertain to specify in one pass. Wayfinder replaces the normal Engineering Grill at the head of the planning flow: name the destination → grill breadth-first with the same engineering/domain discipline → write the durable Wayfinder Map (`wayfinder-map-artifact`) → leave research and prototype decisions as normal planning tickets for the ticket scheduler → advance the decision frontier → hand off to Spec authoring, then tickets, ticket review, and implementation.

Wayfinder reuses the Planning Workflow projection. `wayfinder-map-artifact` writes a separate durable map on the planning workflow, while `planning-tickets-artifact` targets the map ID to store decision tickets through the existing ticket schema and dependency graph. `workflow_wayfinder_map_get` exposes the canonical map to focused workflow turns. A later Spec and its implementation tickets coexist with the map and its decision tickets; the client groups each ticket set by its parent artifact.

### Planning

Planning first creates a dedicated branch and worktree from the selected branch. Setup runs concurrently; only successful completion allows early AppDevStack creation. Grill with Docs starts immediately and follows any interview scope or question limit supplied in the user's prompt; otherwise it resolves the complete product, engineering, and domain frontier. The same thread continues through `planning-spec-artifact`, `planning-tickets-artifact`, and up to `PLANNING_REVIEW_MAX_CYCLES` (5) reviewer sub-threads. A cycle that passes every ticket in its scope ends ticket review, including tickets it corrected itself; only the tickets a cycle explicitly failed carry into the next cycle, which receives that cycle's findings for them. A pass or exhausted review budget automatically launches Implementation with the same worktree, branch, and AppDevStack identity. Missing grill directives recover from the post-turn ready-session event, while startup reconciliation remains the crash-recovery path.

### Implementation

Loads reviewed Planning tickets when present. A prompt-originated run instead invokes the ticket-authoring prompt first, persists a synthetic Spec anchor and durable tickets, and launches automatically from the thread's current branch and worktree.

1. Starts every unblocked ticket concurrently, with no fixed worker cap. Each ticket is an independent cadence with a unique thread, branch, worktree, singleton ticket scope, and App Dev Stack identity. Dependencies branch from the reviewed commit of their blockers.
2. Runs each ticket through three phases: Implementation, optional App Review, and Code Review. Implementation allocates one durable worker thread on the first launch. Recovery appends continuation turns to it and preserves its worktree, branch, tracked and untracked changes, commits, and conversation. A missing durable thread halts the ticket. Ticket App Review resolves its effective E2E and browser scope before provisioning a ticket stack. An empty scope skips the review without creating a stack. Every App Review cycle creates one review thread, one gap-analysis thread when findings exist, and one TDD repair thread. Interrupted phase turns retry in that phase's thread. Ticket Code Review creates one fresh review-and-fix thread per logical cycle, stops early when clean, and runs at most five cycles. Interrupted review turns reuse the current cycle thread and do not consume a logical cycle. Stage claims keep recovery sweeps from duplicating work.
3. A valid failed worker result, a structural Git failure, or an exhausted implementation retry halts automation. Already-running sibling tickets may finish and record their results, but no dependent ticket or integration stage starts while the halt remains. Once every ticket succeeds, one integration thread merges the reviewed ticket branches into the workflow's starting branch and worktree. A real programmatic merge conflict routes the merge-gate agent through the generated `matt-pocock.resolving-merge-conflicts` snapshot before validation. Conflict-free and final gates remain validation-only.
4. Runs one root-scoped combined App Review workflow using its step cycle budget, ten at most. Each cycle has one thread for each ordered phase. Its brief includes cross-ticket flows and every ticket-level warning. Budget exhaustion continues with a warning. A broken prerequisite still halts automation.
5. Runs up to five root-scoped Final Code Review cycles. Each cycle gets one fresh review-and-fix thread and reviews the complete diff from the pinned base. Earlier findings cycles run focused validation. A clean cycle and cycle five run complete validation on the final committed HEAD in that same thread. Review or validation exhaustion records `codeReviewExhaustedAt` and `codeReviewExhaustionReason` as warnings when the branch remains clean and usable. New runs do not create a separate final-validator thread.
6. Runs final validation in a separate thread on the exact latest committed HEAD. Publication requires every configured complete validation command to pass on that HEAD, even after review exhaustion.
7. Publishes the change request from the exact reviewed HEAD. The pull-request body includes ticket and combined App Review warnings, final Code Review exhaustion details, and failed validation evidence. Publication is serialized per implementation run.
8. Starts one durable pull-request babysitter unless the run skips it. The reactor persists a discovered change request before the babysitter claims its thread, so recovery reuses both records instead of creating another pull request or babysitter.

Provider-failure recovery is shared by every autonomous workflow role. Adapters attach a retry disposition, reason, optional HTTP status, and optional `retryAt` to failed turns. The reconciler trusts the terminal turn and projected session; only provider sessions listed as connecting or running suppress recovery. It retries the primary model after one minute, then resolves the reserved `workflow.recovery-fallback` model pin from the workflow root before the standing Settings pin. A valid, distinct backup triggers a server-only fresh-session turn. The provider reactor stops the old adapter session before clearing its cursor and runtime payload; a stop error postpones failover, so two provider writers cannot share the thread. The replacement session keeps the logical thread, stage claim, messages, checkpoints, worktree, and branch. Its bounded prompt identifies the original assignment by message ID, includes the interrupted output tail and proposed-plan reference when present, and restores the required workflow instructions. Retryable failures continue every ten minutes until eight hours from the first terminal failure or 48 attempts. Unknown historical failures stop after two attempts. Exhaustion emits one result through the owning reactor's existing failure path.

`settings.implementation` remains the compatibility default for direct and historical Implementation launches. New composer presets carry their own run-local settings for ticket App Review, combined App Review, final Code Review, pull-request creation, and pull-request babysitting. Implementation translates disabled settings into durable ticket or run skip targets. The Workflows panel can set or lift the same skip targets on one run.

### App Review

App Review is a reusable, restartable loop with a dynamic 1–10 cycle budget. The contract, decider, and shared cycle resolver clamp historical and user-provided values above 10. A launch that sets `previewTargetsPinned` reviews its `previewTargets` verbatim and never looks up an App Dev Stack, so a stack that happens to match the worktree cannot substitute its own frontend and an unhealthy one cannot block the run; an unpinned standalone launch keeps resolving the worktree's stack first and falls back to URLs in the brief. A launch that sets `reviewOnly` is clamped to one cycle by the decider, is skipped by mid-run cycle-budget updates, and stops once its repair tickets validate: the cycle completes and the run finishes `exhausted` without a repair phase, so `thread.app-review-workflow.rerun` rejects `fixing` on it. Cycle 1 always launches a fresh Browser App Review. Duplicate launch/resume events resolve against the latest persisted run, so only one reviewer can claim a cycle. When the target worktree's `t3.json` declares `e2eCommands`, the reactor loads them at each review launch and the reviewer runs them from the worktree before any browser work, with `APP_REVIEW_PREVIEW_URL` (the `APP_REVIEW_PREVIEW_URL_ENV` contract constant) set to the review's first preview target, recording command N as check `e2e-N`. Tickets carry an optional `appReviewScope` (`e2e`, `browser`, or `both`; absent means both) next to `appReviewEligible`; the ticket launch copies it onto the nested run. `settings.workflowStepReviewParts` (keyed like `workflowStepCycles`: the step entry covers standalone and combined reviews and defaults ticket reviews, the ticket sub-step entry overrides it) adds a standing on/off per part, and `thread.workflow.step-review-parts.set` writes the same shape onto the workflow root (`workflowStepReviewParts`, persisted like the step cycle budgets) as a run-level layer that outranks Settings entirely (`resolveLayeredAppReviewStepParts`). `resolveEffectiveAppReviewScope` then intersects the resolved parts × requested scope × availability: a part Settings turn off stays off, while a missing e2e suite merely degrades an e2e request to browser when Settings allow the browser. An empty result skips programmatically: `startTicketAppReview` records a skip warning and goes to Code Review, the combined `startBrowserReview` skips like an explicit stage skip, and a standalone run fails as `automation-unavailable`. Every reviewer launch states its parts in a "Review parts for this run" line. A `browser` scope skips the e2e part and its pass gate; an `e2e` scope tells the reviewer to skip the browser entirely and waives the recording-and-screenshot evidence requirement, with the verdict carried by the check matrix. Those ids are enforced at the pass gate: with commands configured, a pass additionally requires every `e2e-N` check present, passed, and not carried. E2e checks rerun fresh every cycle and are excluded from the carryable list. Failing commands produce findings that flow into gap analysis like any browser finding. The gap analysis is instructed to write test-first tickets, and the fixer prompt requires writing that test before the repair and reporting the e2e commands among its validations. Each cycle is one three-step unit: (1) human-style UI review with durable evidence, (2) gap analysis plus exactly one persisted repair plan after a failure, and (3) execution of that plan. A failed phase spends the current cycle after one interrupted-launch retry. No event path can create cycle 11. A pass ends the run after step one only when its check matrix is non-empty and entirely passed, has no actionable findings, and explicitly verifies every earlier actionable finding by its original ID. The original brief remains the acceptance boundary throughout. The last failed review still completes planning and implementation, then the run ends as `exhausted` because its repaired state cannot be verified within the remaining budget.

### Durable execution limits

An implementation ticket retains its existing `attemptCount` and adds independent generation and launch counters for App Review and Code Review. The run stores the same generation, launch, and valid-pass counters for final Code Review. `automationHalt` records the optional ticket, stage, failure category, detail, and timestamp. Schema decoding supplies zero or null defaults for historical events.

Every autonomous launch checks its expected branch and HEAD before it creates a child. Review and validation require a clean worktree. An interrupted Implementation turn may resume inherited work on the expected branch in the ticket's durable thread. Run-wide repair stages use the existing orchestrator worktree. Continuation prompts require the agent to inspect the diff and recent commits, preserve useful work, finish or repair incomplete work, validate it, commit it, and leave the worktree clean before review continues. The reactor submits an expected-stage claim with the current ticket, stage generation, launch count, and active execution identity. The decider compares that claim with the projected run and rejects stale or duplicate transitions. Restart reconciliation, stale-turn recovery, workflow nudges, and normal event handling all use that claim.

A missing directive or interrupted provider turn may retry once in the same phase or cycle thread. A paused workflow records the continuation without launching it. A worktree on the wrong branch, a missing repository, a deleted durable thread, or an identity that cannot be tied to the workflow sets `automationHalt` immediately. Dirty or newer Implementation work on the expected branch starts a continuation turn. Startup also recognizes persisted interruption halts from older executions, replays successful worker results recorded after the halt, and continues only the interrupted ticket or run-wide stage. A blocked review, invalid repaired branch, exhausted non-interruption retry, or failed final validation still halts the run. Results from already-running siblings are recorded only when their generation and execution identity still match.

An explicit rerun increments only the selected stage generation, resets that stage's launch allowance, and clears a matching halt. It does not reopen other stages. A rerun may claim a fresh thread for the new generation. Recovery within a generation keeps the recorded thread. Code Review restarts at cycle one in a new generation. Completed App Review and Code Review cycles increment logical pass counters; interrupted turns increment launch counters only.

Startup recovery has one coordinator. It loads projections, starts reactor subscriptions without advancing stages, replays persisted provider commands, drains pending thread creation and turn starts, and lets stale-turn recovery settle interrupted sessions. It then reconciles nested App Review runs before parent Implementation and Planning runs. A stage with a pending command or live session is left alone; a stopped or idle stage receives a bounded continuation in its recorded thread. A valid unprocessed result is replayed to the parent controller. A missing or deleted active thread marks the stage for human attention and preserves its worktree and branch. Resource reconciliation then reuses stacks by workflow ownership and normalized worktree path, reapplies successful-ticket tier-down stamps, and tears down completed workflows. Only after every recovery command drains does startup run conservative thread cleanup.

Startup cleanup uses the same orphan predicate as `delete-orphan-workflow-threads.ts`. It deletes only an unreferenced workflow shell with no session, messages, activities, turns or checkpoint, live child, pending provider work, or unfinished workflow reference. It never removes worktrees, branches, commits, artifacts, or meaningful thread history. Cleanup counts are logged, while App Dev Stack ownership conflicts are returned by stack diagnostics instead of being resolved destructively.

Standalone panel launches create a dedicated controller child and edit the selected worktree in place, including unrelated dirty WIP. A new composer draft becomes its own top-level controller. Embedded runs put the controller below Implementation and require each implementation step to leave a clean committed HEAD. Invalid automation—unavailable review tooling, malformed or missing plans, implementation failure, unexpected interaction, or a stale workspace fingerprint—ends the run as `failed` with diagnostic metadata rather than introducing another verdict.

`projection_app_review_workflow_runs` stores canonical run JSON. Each run records caller and target identity, original brief, preview targets, cycle budget, ordered reviewer/plan/fixer history, the active phase, HEAD and diff-hash fingerprint, terminal outcome, and timestamps. Launch, update, cancel, and refreshed-preview resume commands produce projected run events; `AppReviewWorkflowReactor` reconciles every nonterminal run after restart without polling.

## Workflow identity and links

`workflowPreset` identifies the selected workflow definition; it is not a run identity. Every new top-level run receives a durable `workflowId`, and every child owned by that run inherits it. A nested controller such as App Review receives a new `workflowId` and stores the enclosing run as `parentWorkflowId`. AppDevStack ownership uses the durable run ID, so it follows the implementation worktree rather than a transient thread.

The web thread route accepts `?workflow=<workflowId>`. A copied workflow link targets the top-level thread route, opens the Workflows panel, expands the matching run, and keeps the workflow query while navigating among its child threads. The explicit parent link is also what nests App Review under its invoking Fast Feature or Implementation run when physical thread ancestry is incomplete. The panel takes its ordered step labels directly from `WORKFLOW_PRESET_DEFINITION_BY_ID[preset].helpSteps`; runtime threads attach to those definitions, and repeated review or repair threads render as cycles of one step. A human-blocked implementation stage exposes the existing stage-scoped retry command directly on its matching step, preserving the run and its workspace state.

## Orchestration

`ProductWorkflowReactor.ts` launches Fast Feature from its proposed Plan and drives Full Feature from locked product intent; its Fix branch and Fast Feature Product Grill support remain only for historical runs. First-turn bootstrap owns the shared workflow worktree, starts Fast Feature Planning or the selected Grill immediately, waits for the repository-declared setup terminal to complete, and then creates AppDevStack. `ImplementationWorkflowReactor.ts` reuses that workspace and stack, owns ticket-worker worktrees, the merge pipeline, AppDevStack probing, composition with App Review, and change-request publication. `AppReviewWorkflowReactor.ts` owns the three-step review, same-thread planning, and new-thread implementation cycles. Caps live in the contracts (`PLANNING_REVIEW_MAX_CYCLES`, `APP_REVIEW_WORKFLOW_DEFAULT_CYCLES`, and `APP_REVIEW_WORKFLOW_MAX_CYCLES`). Shared sub-agent conventions (stage IDs, MCP tools, directives) are in `apps/server/src/provider/WorkflowSubagentInstructions.ts`.
